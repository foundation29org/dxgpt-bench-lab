## Prerequisites

### 1. Environment Variables

Create a `.env` file in the **project root** (`C:\repo\DxGPT\eval\.env`) with the following variables:

```env
# Azure Text Analytics (for medical code attribution)
AZURE_LANGUAGE_ENDPOINT=https://your-endpoint.cognitiveservices.azure.com
AZURE_LANGUAGE_KEY=your_azure_key

# Azure OpenAI (for LLM models)
AZURE_OPENAI_ENDPOINT=https://your-endpoint.openai.azure.com
AZURE_OPENAI_API_KEY=your_azure_openai_key
AZURE_OPENAI_API_VERSION=2024-02-15-preview

# Google Gemini (for Gemini models)
GOOGLE_GENAI_API_KEY=your_gemini_key
# Or alternatively:
GEMINI_API_KEY=your_gemini_key

# Azure Translator (optional, for case translation)
AZURE_TRANSLATOR_KEY=your_translator_key
AZURE_TRANSLATOR_ENDPOINT=https://api.cognitive.microsofttranslator.com
AZURE_TRANSLATOR_REGION=your_region

# Hugging Face (for BERT similarity)
HF_TOKEN=your_huggingface_token
SAPBERT_ENDPOINT_URL=your_sapbert_endpoint
```

### 2. Python Dependencies

Install the required dependencies:

```bash
pip install -r requirements.txt
```

Or using `uv`:

```bash
uv pip install -r requirements.txt
```

### 3. Dataset

Make sure you have the dataset at the path specified in `config.yaml`. By default:
- `bench/datasets/all_150.json`

## Evaluation Steps

The pipeline executes **3 main steps** in sequence:

### **STEP 1: Emulator (DDX Generation)**

**What does it do?**
- Reads each case from the dataset
- Sends the case to the configured LLM model (GPT-5, Gemini, etc.)
- The LLM generates differential diagnoses (DDX) based on the clinical case
- Optionally translates the case if `TRANSLATE_CASE.ENABLED: true`

**Input:**
- JSON dataset with clinical cases (`all_150.json`)

**Output:**
- JSON file with DDX generated by the LLM
- Location: `output/<dataset>/<prompt>/<model>/ddxs_from_emulator.json`

**Estimated time:**
- Depends on the model and number of cases
- Gemini 2.5 Pro: ~75 seconds for 150 cases (with tier 1)
- GPT-5.1: ~13-14 seconds per case

---

### **STEP 2: Medical Labeler (Medical Code Attribution)**

**What does it do?**
- Takes the DDX generated in Step 1
- For each differential diagnosis, calls Azure Text Analytics
- Azure identifies medical entities and extracts codes:
  - **ICD-10**: International classification codes
  - **SNOMED**: Standardized clinical terminology
  - **OMIM**: Gene and phenotype database
  - **ORPHA**: Rare diseases

**Input:**
- JSON file with DDX from Step 1

**Output:**
- JSON file with DDX + assigned medical codes
- Location: `output/<dataset>/<prompt>/<model>/ddxs_from_labeler.json`

**Estimated time:**
- ~5-10 minutes for 150 cases (depends on Azure Text Analytics)

**Note:** The emulator file is automatically deleted after this step.

---

### **STEP 3: Evaluator (Quality Evaluation)**

**What does it do?**
- Compares the generated DDX with reference diagnoses (GDX)
- Uses **3 evaluation methods** in priority order:

  1. **SNOMED Match**: Exact SNOMED code match
  2. **ICD-10 Match**: ICD-10 code match (exact, parent, child, sibling)
  3. **Semantic Match**: Semantic similarity using BERT + LLM judgment

**Acceptance criteria:**
- **BERT_AUTOCONFIRM_THRESHOLD** (0.90): If BERT score ≥ 0.90, automatically accepts (doesn't call the LLM)
- **BERT_ACCEPTANCE_THRESHOLD** (0.80): If BERT score ≥ 0.80, requires LLM judge confirmation
- If BERT < 0.80, the **LLM judge** decides if there's a match (see [Judge Model](#judge-model-judge_model) section below)

**Input:**
- JSON file with DDX + codes from Step 2
- Original dataset with GDX (reference diagnoses)

**Output:**
- `evaluation.log`: Detailed process log
- `evaluation_details.txt`: Details of each evaluated case
- `summary.json`: Statistical summary of results
- Location: `output/<dataset>/<prompt>/<model>/<timestamp>/`

**Estimated time:**
- ~5-10 minutes for 150 cases

## Pipeline Configuration

Edit the `config.yaml` file to customize the evaluation:

### LLM Model

```yaml
DXGPT_EMULATOR:
  MODEL: "gemini-2.5-pro"  # Options: "gpt-5.1", "gpt-5-mini", "gemini-2.5-pro", "gemini-2.0-flash", etc.
```

**Available models:**
- **Azure OpenAI**: `gpt-5.1`, `gpt-5-mini`, `gpt-4o-summary`, `o3-mini`
- **Google Gemini**: `gemini-2.5-pro`, `gemini-2.0-flash`, `gemini-3-pro-preview`

### Model Parameters

```yaml
PARAMS:
  temperature: 0.1          # Creativity (0.0 = deterministic, 1.0 = creative)
  max_tokens: 12000         # Maximum tokens in response
  reasoning_effort: "low"   # For O3/GPT-5: "low", "medium", "high"
  thinking_level: "low"     # For Gemini 2.5/3: "low", "medium", "high"
```

### Case Translation

```yaml
TRANSLATE_CASE:
  ENABLED: true             # Enable/disable translation
  TARGET_LANGUAGE: "en"     # Target language ("en" = English, "es" = Spanish)
```

**When to use translation?**
- If your dataset has cases in Spanish and you want to evaluate the model in English
- May improve performance if the model is better trained in English

### Evaluation Thresholds

```yaml
EVALUATOR:
  BERT_ACCEPTANCE_THRESHOLD: 0.80   # Minimum score to consider a match (0.0-1.0)
  BERT_AUTOCONFIRM_THRESHOLD: 0.90  # Score to automatically accept (0.0-1.0)
  ENABLE_ICD10_PARENT_SEARCH: true  # Search for parent codes in ICD-10
  ENABLE_ICD10_SIBLING_SEARCH: true # Search for sibling codes in ICD-10
  JUDGE_MODEL: null  # LLM model to judge semantic matches (optional)
```

**Recommendations:**
- **BERT_ACCEPTANCE_THRESHOLD**: 0.80 is conservative, 0.70 is more permissive
- **BERT_AUTOCONFIRM_THRESHOLD**: 0.90 is standard, don't change unless there are issues
- **JUDGE_MODEL**: Model used to judge if there's a semantic match when BERT < 0.80

### Judge Model (JUDGE_MODEL)

The judge model is the LLM that decides if there's a semantic match when the BERT score is below the threshold. By default, it uses **automatic logic**:

**Automatic behavior (JUDGE_MODEL: null):**
- If you're evaluating a **Gemini** model (e.g.: `gemini-2.5-pro`) → the judge will be the **same Gemini model**
- If you're evaluating an **OpenAI** model (e.g.: `gpt-5.1`, `gpt-5-mini`, `o3-mini`) → the judge will be **`gpt-4o-summary`**

**Manual configuration:**
```yaml
EVALUATOR:
  JUDGE_MODEL: "gemini-2.5-pro"  # Forces using this model always
  # Or
  JUDGE_MODEL: "gpt-4o-summary"  # Forces using GPT-4o-summary always
```

**Why use the same model?**
- **Consistency**: If you evaluate Gemini, the judge is also Gemini (more accurate)
- **Precision**: The same model judges its own responses
- **Neutrality**: For OpenAI, using `gpt-4o-summary` avoids bias from the evaluated model

**Example:**
- Evaluating `gemini-2.5-pro` → Automatic judge: `gemini-2.5-pro`
- Evaluating `gpt-5-mini` → Automatic judge: `gpt-4o-summary`
- Evaluating `gemini-2.0-flash` → Automatic judge: `gemini-2.0-flash`

### Pipeline Control

```yaml
MAIN:
  SHOULD_EMULATE: true   # Step 1: Generate DDX using the LLM model
  SHOULD_LABEL: true     # Step 2: Assign medical codes using Azure Text Analytics
  SHOULD_EVALUATE: true  # Step 3: Evaluate DDX against GDX
```

**Common use cases:**

| Scenario | SHOULD_EMULATE | SHOULD_LABEL | SHOULD_EVALUATE | Description |
|----------|----------------|--------------|-----------------|-------------|
| **Full execution from scratch** | `true` | `true` | `true` | Executes all steps (or omit these values) |
| **Re-evaluate only** | `false` | `false` | `true` | Uses existing DDX and codes, only re-evaluates |
| **Generate DDX only** | `true` | `false` | `false` | Generates diagnoses but doesn't assign codes or evaluate |
| **Generate DDX + codes** | `true` | `true` | `false` | Generates DDX and assigns codes, without evaluating |
| **Assign codes only** | `false` | `true` | `false` | If you already have DDX, only assigns medical codes |

**Note:** If you omit these values, the pipeline assumes `true` by default (executes all steps).

## Execution

### Full Execution

```bash
# From the pipeline directory
cd "bench/pipelines/pipeline_v4 - fork/main"

# Run complete pipeline
py main.py
```

### Step-by-Step Execution

If you want to run individual steps:

```bash
# Step 1 only: Generate DDX
py emulator.py

# Step 2 only: Assign medical codes
py medlabeler.py

# Step 3 only: Evaluate
py evaluator.py
```

### State Management

The pipeline automatically detects if results already exist:

**If DDX from Step 1 exists:**
```
⚠️  DDX results already exist at output/...

1. Re-run DDX generation (will overwrite existing results)
2. Continue with medical code labeling using existing DDX
3. ❌ Abort operation

Enter your choice (number):
```

**If codes from Step 2 exist:**
```
⚠️  Labeled results already exist at output/...

1. Re-run medical code labeling (will overwrite existing results)
2. Continue with evaluation using existing labeled results
3. ❌ Abort operation

Enter your choice (number):
```

## Interpreting Results

### `summary.json` File

Contains the main metrics:

```json
{
  "total_cases": 150,
  "successful_matches": 52,
  "success_rate": 0.347,
  "ddx_positions": {
    "P1": 42,  // Correct diagnosis in position 1
    "P2": 8,   // Correct diagnosis in position 2
    "P3": 1,   // Correct diagnosis in position 3
    "P4": 1    // Correct diagnosis in position 4
  },
  "average_position": 1.250
}
```

**Key metrics:**
- **success_rate**: Percentage of cases where the correct diagnosis was found
- **P1, P2, P3, P4**: Distribution of positions where the diagnosis was found
- **average_position**: Average position of the correct diagnosis (lower is better)

### `evaluation.log` File

Detailed log with the result of each case:

```
[1/150] BERT_AUTOCONFIRM → GDX[1]: Systemic lupus erythematosus | DDX[1]: Systemic Lupus Erythematosus → **P1**
[2/150] SEMANTIC → NO_MATCH → **REJECTED**
[3/150] BERT_AUTOCONFIRM → GDX[1]: POEMS syndrome | DDX[2]: POEMS Syndrome → **P2**
```

**Result codes:**
- `BERT_AUTOCONFIRM`: Match found with BERT score ≥ 0.90
- `BERT_ACCEPTANCE`: Match found with BERT score ≥ 0.80 (confirmed by LLM)
- `SNOMED`: Match found by SNOMED code
- `ICD10_EXACT`: Match found by exact ICD-10 code
- `ICD10_PARENT`: Match found by parent ICD-10 code
- `ICD10_SIBLING`: Match found by sibling ICD-10 code
- `SEMANTIC`: Match found by semantic similarity (LLM)
- `NO_MATCH` / `REJECTED`: No match found

### `evaluation_details.txt` File

Contains detailed information for each case, including:
- Evaluated GDX (reference diagnosis)
- Generated DDX (differential diagnoses)
- BERT scores for each DDX
- Complete evaluation trace (SNOMED → ICD-10 → Semantic)

## Troubleshooting

### Error: "Azure Language service credentials not found"

**Solution:**
- Verify that the `.env` file is in the project root (`C:\repo\DxGPT\eval\.env`)
- Verify that `AZURE_LANGUAGE_ENDPOINT` and `AZURE_LANGUAGE_KEY` variables are configured

### Error: "Module not found"

**Solution:**
```bash
pip install -r requirements.txt
```

### Error: "429 RESOURCE_EXHAUSTED" (Gemini)

**Cause:** Rate limit exceeded

**Solution:**
- The code already includes automatic delays based on the model
- For free tier, delays are longer (30s for 2.5-pro)
- With billing (tier 1), delays are shorter (0.5s for 2.5-pro)
- If it persists, increase the delay in `emulator.py`

### Many "REJECTED" cases

**Possible causes:**
1. **Medlabeler didn't assign codes**: Check `medlabeler.log` to see if Azure returned codes
2. **BERT threshold too strict**: Consider lowering `BERT_ACCEPTANCE_THRESHOLD` to 0.70
3. **LLM too conservative**: The LLM may be rejecting valid matches

**Solution:**
- Review `evaluation_details.txt` for specific cases
- Check BERT scores in rejected cases
- If scores are high (>0.65) but don't reach the threshold, consider lowering it

### Pipeline stops mid-execution

**Solution:**
- The pipeline automatically saves state
- You can resume from where it stopped by running `py main.py` again
- Choose the "Continue" option when asked about existing files

### Different results between executions

**Cause:** LLM models can have variability even with `temperature: 0.1`

**Solution:**
- This is normal, especially with non-deterministic models
- For fair comparisons, use the same `seed` if the model supports it
- Run multiple times and average the results

## Tips and Best Practices

1. **Start with a small dataset**: Test with 5-10 cases before running 150
2. **Review the logs**: `.log` files contain valuable error information
3. **Compare models**: Run the same configuration with different models to compare
4. **Save configurations**: The pipeline automatically saves a copy of `config.yaml` in each run
5. **Monitor rate limits**: Especially with Gemini models on free tier
6. **Review specific cases**: Use `evaluation_details.txt` to understand why a case was rejected
